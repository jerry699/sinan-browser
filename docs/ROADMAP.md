## 0. 上游跟踪策略（持续执行）

上游 [VictorKildahl/cra](https://github.com/VictorKildahl/cra) 仍在活跃开发。我们的同步原则：

1. **节奏**（2026-11-21 用户指令）：**每 1–2 周更新一次**——每周日自动化巡检（源码 + 引擎），有更新就发版；源码大合并的目标节奏 2–3 周（11-17 的 346-commit 合并花了两个会话，513-commit 的架构迁移是特例）。
2. **机制**（2026-11-21 迁移后更新）：上游新提交进 `origin/main` → **merge** 进主线 `sync-wip-20261120`（不再 rebase daily——迁移后主线以「上游为基座 + 司南特性移植」模式维护，参考 6b6efe54）→ 构建验证 → 跑回归。
3. **引擎**：上游已从「修补版 CEF」迁移到**完整 Chromium 构建**（`scripts/fetch-engine.sh` → Cra Framework.framework；CEF 路径保留为回退 `CRA_ENGINE=cef`）。引擎版本看上游 Engine pre-release（`gh release list`），x64 资产名 `cra_framework_x64.tar.xz`。基线：2026-11-21 起 = Engine 159.0.8154.13（CEF 156 为回退）。下载慢时走代理 127.0.0.1:7890（8 段并行 Range 更快）。
4. **回归必跑**：`scripts/recall-eval.py`（检索 hit@1 基线 16/31，hit@4 20/31，RRF k=60）+ `swift build` 零错误 + Intel 构建。
5. **冲突面控制**：迁移后模式 = 上游文件整用上游的，司南特性作为移植层（TidyPreferences 独立文件、服务 DI 闭包里接 Max 管线、store 移植块）。新功能评审必问：**自己的文件吗？上游文件里加了几行？**
6. **每周日自动化**（已更新 2026-11-21）：拉上游 → merge 主线 → 引擎版本检查 → 构建验证 → 有更新才发版 → 简报。构建失败：中止并报告，绝不自动发布。
7. **上游重叠警戒**：上游的 MCP/Agent 层与我们「不做 Agent」哲学相逆——保持默认关闭；上游若做本地模型，评估吸收而不是分叉。

## 新增需求（2026-11-23 记录，用户提出的三方向）

### 1. 兴趣更新摘要（兴趣雷达）——与模型训练一并考虑

根据用户日常浏览喜好，主动搜索/追踪其感兴趣内容的更新并总结给用户（如"你关注的 零跑新车型/Qwen 新版本/某博主，本周有这些动态"）。

- **现有地基（大部分已就绪）**：P3 语义索引（兴趣画像 = 历史+嵌入）、dwell 行为信号（喜好强度）、RRF 融合、本地模型摘要管线（划选翻译同款）、SinanMenu 扩展桥（推送入口）
- **形态**：不自动爬全网——用户"订阅"来源（常访站点/关键词/收藏夹），每周/每日后台拉新内容 → 兴趣相似度过滤 → 本地模型总结成一张简报卡片（侧栏/新标签页），点击进原文
- **训练关联**：多文档中文摘要 + 时效性表述（"本周新增…"）；弃答训练（无更新时明确说"没有新动态"，不编造）；来源域名理解。与 TRAINING-PLAN §11 的浏览领域模型合并考虑
- **隐私红线**：全部本地执行；拉取请求不含用户画像，只按订阅源匿名抓取

### 2. 内容整理与转写纠错——与模型训练一并考虑

蒸馏笔记/转写（Whisper small）的中文错误仍多：专有名词、技术术语、同音字。

- **分层改进**：(a) 热词注入（用户领域词汇表 → 转写后处理规则，不需要训练）；(b) 转写纠错模型：用 TTS→ASR→原文 对比**自动合成训练对**（错误转写 vs 正确文本），QLoRA 微调纠错任务——数据管线零人工；(c) P5 式用户纠错回路：用户改过的词被记住，下次优先
- **训练关联**：纠错模型与兴趣摘要模型可共享一个 0.6B 多任务底座（TRAINING-PLAN §11 的浏览领域模型加两个任务：summarize-updates、correct-transcript）
- **验收**：B 站技术区视频蒸馏错误率对比（基线 whisper-small vs +纠错）

### 3. 与国内主流办公 Agent 产品结合（MCP）

把司南做成对国内 Agent 产品**有用的本地能力源**，而不是又一个聊天入口。

- **定位**：司南作为 MCP 服务器暴露浏览器能力：历史语义搜索、页面内容读取、蒸馏笔记库、打开/整理标签——钉钉 AI 助理、飞书、通义、智谱清言等通过标准 MCP 协议接入
- **现状**：上游已有 MCP 层（我们默认关闭）→ 评估吸收 + 增加国内产品预设；扩展桥（SinanMenu）已打通扩展→应用通道，MCP 是另一条独立通道
- **隐私红线（硬性）**：每个工具单独授权、默认全关、用户可见的连接管理界面；"AI 悄悄帮忙"原则不因集成而破例
- **优先级**：工程先行（无训练依赖）；等 1/2 落地后再排期，避免同时开三条战线
